X-Rayderived memoryone binary, two modes

Parse, embed, snapshot, serve

X-Ray serves derived memory: a semantic graph reconstructed from repositories, documentation and Kubernetes manifests. Nothing in it is authored, so anything in it can be thrown away and rebuilt. This page is how that rebuild works, end to end, what the parser reads, what the embedder is given, what a .gob.gz actually holds, and what happens when you type a query.

Two passes, and they are not the same size. Building a map embeds every node once; answering a query embeds the query, once. The snapshot between them is what keeps those apart.

01

What Tree-sitter does

internal/parser/lang.go
walk.go · tags.go

Tree-sitter is a parser generator. Each language ships a grammar; the grammar is compiled into the X-Ray binary, so there is nothing to install alongside it and no language server to run. Given a file, it produces a full syntax tree, not a regex guess at what a function looks like, but the language's own structure, with exact line ranges for every declaration.

Two ways of reading that tree are in use here.

  • The rich extractor (Go). A hand-written walk over the tree in two passes: first the file's scope, its imports and every name it declares, then the nodes and edges themselves. It carries the evidence each call site has (the package an identifier came from, a receiver's declared type, the root of a chain) into the edge, for the linker to spend later.
  • The generic extractor (ten other languages). Most grammars ship a tags.scm query, a pattern that captures definitions and references. Those queries are vendored into the binary and run as-is: whatever they capture as a definition becomes a node, whatever they capture as a call becomes an edge from the definition containing that line. No Go code is written per language.

Adding a language is therefore two steps: register its grammar and file extensions in parser/lang.go, and drop its tags.scm into parser/queries/.

.ts and .tsx are separate grammars sharing one tags query and one language label, so both land in the same search space. An unknown extension returns nothing and no error, which is what lets the walk skip-scan a tree cheaply.

What is deliberately not Tree-sitter parsed

Markdown structure is heading-based, so a chunker is enough: one Doc node per file, one Section per ## heading. Kubernetes YAML gets a tolerant line scan instead of a strict parse, because a Helm template holding {{ .Values.image }} is not valid YAML and a real parser would fail on exactly the files most worth indexing. It reads files only, no cluster is contacted.

02

From files to a graph

internal/engine/parse.go
internal/graph/link.go

The walk skips what isn't yours, .git, node_modules, vendor, dist, build, .venv, __pycache__, plus minified bundles, which parse as one enormous line. It will not descend a symlinked directory unless told to: otherwise the shape of every future build depends on wherever a repo happens to point.

Extraction gives you symbols and unresolved calls: a call site names a function, it does not name a definition. The linker turns one into the other using five rules, each looking only where its own evidence points. Go's builtins (append, len, make) are dropped first, they are not call-graph edges.

Repo-wide name matching used to exist as a last resort. It linked a test calling the Kubernetes client's promoted Update() to engine.Indexer.Update, the only Update declared anywhere, and pulled an unrelated package into a blast radius. Ambiguity now yields no edge, which is why a graph of this repo has no edge pointing at the standard library.

03

What gets embedded

internal/index/index.go
nodeText

An embedding turns text into a vector, a list of numbers positioned so that text with similar meaning lands nearby. That is what makes a paraphrase findable: you do not have to know the function's name.

A node is not embedded as its source. nodeText composes a deliberate string: documentation embeds its own prose; a file becomes a one-line description; a code node leads with its signature and path, then folds in up to 600 characters of its body. Leading with the signature keeps exact-name queries strong, and the body slice is what lets a paraphrase reach the right function at all. 

// what nodeText composes for one Go method
Func Indexer.Graph() *graph.Graph
  in internal/engine/indexer.go
↳ then ≤600 chars of the declaration body ----------------
  func (ixr *Indexer) Graph() *graph.Graph { return ixr.g }

Where the vectors come from

Any OpenAI-compatible /v1/embeddings endpoint you run yourself, llama.cpp, Ollama, vLLM, LM Studio. The default assumes http://localhost:8090 serving nomic at 256 dimensions, with an 8,192-character cap so an oversized node is truncated rather than rejected. This is the only part of the system that is not local computation, and it is still your own process.

Why the cache is keyed by text

Every rebuild constructs fresh node objects, so a cache keyed by node identity would miss on everything. Keyed by the composed text, an unchanged function reuses its vector and never reaches the embedder, which is why re-indexing one edited file costs one or two embed calls, not thousands. The same fact cuts the other way: change what nodeText composes and every snapshot ever built is stale.

The model, and why 256 dimensions

The default is nomic-embed-text-v1.5: 137M parameters, Apache-2.0, with weights, training data and training code all published. It accepts 8,192 tokens, which is why nothing here has to chunk a function into pieces and stitch the results back together.

What makes a 256-dimension vector safe is how the model was trained. Matryoshka representation learning nests the information: the training loss is applied to the first 64 components, the first 128, the first 256 and so on, so every prefix of the vector is a working embedding in its own right. A 256-dimension vector here is not a 768-dimension vector with two thirds discarded. It is the 256-dimension embedding the model was trained to produce.

MTEB averages as nomic publishes them for this model. Bytes are 4-byte floats, one vector per node, before gzip. Every row comes from one set of weights, so the dimension is a serving choice, not a different model or a second download.

Section 10 has the measurement that settled it: on this project's own corpus, full 768 dimensions scored +0.2 points over the 256 truncation. MTEB puts the gap at 1.24. Either figure buys three times the bytes per vector, so 256 is the default and -embedding-dims is there for anyone whose corpus disagrees.

Why the slice happens in this process

The OpenAI-compatible API has a dimensions parameter, and X-Ray deliberately does not send it. Two gateways decided that: llama.cpp ignores the parameter and returns native dimensions anyway, and Ollama truncates without renormalizing afterwards, which yields measurably worse vectors than the proper procedure. So the reduction happens here, in truncateNormalize: keep the first 256 components, then divide by the new L2 norm. Doing it on this side is uniform across every gateway, and the fingerprint recorded in a snapshot is then guaranteed to describe the vectors that are actually in it.

The renormalize step is not optional. A slice of a unit vector is not a unit vector, and cosine similarity computed on vectors that are not unit length is not cosine similarity; the scores come out skewed in favour of whichever vectors happened to keep more of their length. Nomic's reference snippet also layer-norms before slicing, which a gateway has already done by the time it hands back a pooled, normalized vector, so what is left for this side is the slice and the renorm.

One thing the model asks for and this does not send: a task prefix. The model card wants search_document: on text being indexed and search_query: on a query, which is how it tells the two roles apart. Here every text reaches the gateway as written, and the task name only keeps a query's cached vector from colliding with the same string cached as a document, so queries and nodes share one symmetric space. Adding the prefixes would change the embedded text, and by the rule above that invalidates every vector in every snapshot, which makes it an experiment to measure rather than a flag to flip.

04

The .gob.gz snapshot

internal/engine/snapshot.go
hnswcodec.go

A gob is Go's own binary serialization format, the language's equivalent of a pickle: compact, self-describing about types, and much faster to read than JSON. A map's snapshot is one gzipped gob file, <label>.graph.gob.gz, and it is the whole point of the design: it carries the parsed graph and every vector and the built search index, so loading it is neither a parse nor an embed pass.

The file holds two values written one after the other, and that order matters. A reader can decode the first, learn what the map is, and stop, which is how a server can register dozens of maps at startup without decoding a single graph.

Meta is opaque: attributes X-Ray round-trips for other tools and never reads itself. HNSW is additive, an older snapshot without it simply decodes as absent and the index is rebuilt on load.
ValueWhen it is readWhat it holds
Headerat registration, always resident Version · Label · RepoPath · BuiltAt · Fingerprint{Model, Dims, MaxInputChars, MaxInputTokens} · Nodes · Edges · Summary · SummarySource · SummaryVec
Bodyon the map's first hit Files (parsed nodes + edges, per path) · Cache (nodeText → vector) · HNSW (the built index) · Meta

Building one

This is the one and only pass that embeds every node. It needs the parser, so it needs the full (CGO) build; everything afterwards does not. 

# parse, embed and write ~/.xray-maps/myapp.graph.gob.gz
xray graph snapshot -repo myapp=/path/to/myapp -snapshot-dir ~/.xray-maps

# serve every snapshot in that directory, parser-free
xray graph serve-snapshots -snapshot-dir ~/.xray-maps -addr :8084

The fingerprint

A snapshot is only valid for a server embedding into the same space. A Dims mismatch is a hard rejection, those vectors are not comparable to a query embedding, and a silent mismatch would return confident nonsense. A model name difference only warns: a llama.cpp sidecar serves whatever GGUF is loaded regardless of the label it is called by.

Why the index ships inside

The search index (HNSW, a navigable graph of vectors, so a query visits a few hundred neighbours instead of scoring all of them) is expensive to build and cheap to read. Rebuilding it on load costs seconds for a few thousand nodes, and it recurs on every restart and after every idle eviction. Carrying it in the file turns that into a read.

05

Serving many maps at once

internal/engine/registry.go

One process serves many maps, and there is no merged graph: each keeps its own graph, its own index and its own vector cache, so ranking never bleeds between projects and a whole map's memory drops in one eviction. Idle maps are evicted after a TTL if one is set; their routing vector stays resident, so they remain reachable and reload from disk on the next hit.

A query naming a map is a free fast path, no embedding needed to route it. A query that names none is embedded once and cosine-ranked against every resident summary vector; -route-fanout decides how many of the best-matching maps actually get searched. Where a map's summary came from is recorded (explicit, readme, or a fallback built from symbol names), because a routing input you cannot inspect is one you cannot debug.

Illustrative shape, not a real directory listing. What matters is the spread: one large repository can outweigh every other map put together, and the small ones cost almost nothing to keep registered, because registration reads each header and stops there.

06

How a search runs

internal/index/index.go
lexical.go

One embed call per search, the query string, nothing else. Then two channels run over the chosen map and their results are merged.

  • Semantic. The query vector walks the HNSW index for nearest neighbours by cosine distance. It deliberately over-fetches, because kind and repo filters are applied after the fetch and would otherwise thin the list below what you asked for.
  • Lexical. Per-word trigram postings, plain keyword matching. It exists because an embedding can lose a query whose exact terms appear repeatedly in the target: a rare identifier the model never encoded well is exactly the kind of thing you search for. When a query carries no usable tokens it abstains rather than voting arbitrarily.

The two are combined by reciprocal rank fusion: each result scores 1/(60+rank) in each channel and the sums are added. Ranks, not scores, cosine sits in a narrow band while the keyword score is an unbounded integer, so only positions can be meaningfully compared. Something ranked 8th semantically and 1st lexically still surfaces.

How a keyword matches, and why there is no Levenshtein pass

The obvious way to tolerate a typo is edit distance: count the single-character insertions, deletions and substitutions that turn one word into another, and accept a word if that count is small. That is the Levenshtein algorithm, and it is what the earlier implementation of this search used. It is also quadratic in the length of the two words, and it has to run for every query token against every word of every candidate, which is why it grew into the dominant cost of a search as the corpus grew.

This index does the same job with set overlap instead. Every word is reduced at index time to its three-character slices, so parser becomes par, ars, rse, ser. A query token matches a word when enough of their slices coincide, and "enough" scales with length, because one wrong character costs a short word proportionally more than a long one.

A typo inside a long word still matches, because it only spoils the two or three slices that span it. Long words are held tight on purpose: at 90% overlap, near-miss neighbours with similar spellings do not collide.
Token lengthOverlap requiredEffect
Very short (1 to 2 slices)100%must match exactly; the token more or less is its own slice
Medium (3 to 4 slices)75%tolerates roughly one substitution
Long (5 or more)90%tight, to keep similar long words apart

A candidate then has to match a share of the query's tokens, not all of them. Demanding every token is wrong for a question asked in words: "who is supposed to write the implementation code on this project?" carries "supposed", which the right document may never contain even though it contains every other token several times. Roughly two thirds is the gate; matching all of them still wins on rank.

Replies are deliberately lean: five ranked pointers by default, twenty at most, each with a short preview. You pay for the one node you actually open, not for a file dump.

08

Keeping it current

internal/engine/update.go

The serving process holds the live graph, so keeping it current is a small message, not a rebuild. Changed files are re-parsed, and because the vector cache is keyed by text, only genuinely changed nodes reach the embedder. A one-file edit lands in roughly 10–70 ms.

The reply counts changed, removed and skipped separately, and names paths belonging to no served map as unowned, so an update that indexed nothing says so, instead of passing as a success. skipped matters in the parser-free build: it cannot read code files, and silently treating "no nodes" as "file deleted" would empty a graph. 

# after an edit, from anywhere
xray graph update path/to/file.go

# or let the agent do it: `xray graph install` drops a PostToolUse
# hook into .claude/ that calls update_code_graph on every write
09

Watching it work

internal/hub
/ws

Every search publishes a hit event on a WebSocket at /ws: the qualified names it returned, their kinds, and the query. The graph page listens, and lights the region those hits landed in, the whole category washes brighter and dims back down over about twenty seconds, so a search is still legible seconds after it happened. Re-indexing publishes a change event the same way.

That is the point of the visualisation: not decoration, but a way to see which part of the corpus an agent is actually working in, from the outside, without reading its transcript.

Does it find the right thing?

Latency says nothing about whether the answer was correct, so the repository carries an eval that measures retrieval quality directly. It builds a snapshot of this codebase into a temporary directory, serves it on a spare port, runs a fixed set of probes against it, then throws both away. Nothing persistent is read or written.

Five dimensions are scored separately, so a regression names itself instead of moving one blended number. Run it with make eval; add EVAL_BASELINE=<file> to diff against a stored run, which exits non-zero if recall or MRR falls more than five points or median latency rises by more than half.

One run against this repository, 737 nodes. MRR is mean reciprocal rank: 1.0 means the right answer was always first, 0.5 means it was typically second.

Known limitation, stated plainly

Change-risk scoring undercounts callers across package boundaries: the linker treats pkg.Func() as external, which is right for a third-party call and wrong for a call into another package of the same repo. A LOW rating can therefore be under-confident. The same eval work that produced the numbers above is what found it, along with a search that silently starved rare node kinds once the corpus outgrew its result window, which was fixed by scanning that kind exactly instead of filtering a global top-K.

How this compares

public benchmarks
measured on the memory substrate, not this graph

Read this section knowing what it does and does not cover. The agent-memory market publishes on two benchmarks. LongMemEval (500 questions about facts buried in ~115k tokens of past conversation) and LoCoMo (1,986 questions over ten long dialogues). Those measure a conversational memory substrate. They were run against X-Ray's cell store, which shares this project's retrieval machinery, the same hybrid lexical + HNSW search, the same RRF fusion, the same 256-dimension embeddings, but not its code parsing. What transfers is what the numbers say about retrieval design.

The reader model matters as much as the memory system, so only same-reader comparisons are fair. Caveats that depress these numbers and are not hidden: one search per question (a deployed agent issues several), no reranker, no query rewriting, and a judge measured 2–3 points harsher than the gold standard on spot-checks.

Reading published numbers

There is no official leaderboard; every circulating one is run by a vendor. Three things are worth checking before comparing any two figures.

  • Which reader answered. The same memories scored 54.0 with a small model and 65.6 with a large one. Reader progress alone moved the theoretical ceiling from about 87 to about 92.
  • Retrieval or accuracy. Several headline figures are recall, whether the right document was fetched, printed beside accuracy numbers. One vendor's "95%" is recall; its answer accuracy is 81.6.
  • Who judged. Self-judged runs, invented weighted metrics and README-only claims all appear. Independent reruns have landed 11 points below a published claim for the same system.

The finding that settled a choice here

Full 768-dimension embeddings scored +0.2 points over the 256-dimension truncation, and fetching deeper candidate lists gained +4.1 before flattening out. That is why this ships 256 dimensions: on the measurement, the smaller vector performs the same, and a snapshot is a quarter of the size.

Against a temporal knowledge graph (Zep / Graphiti)

Graphiti tops LoCoMo with a knowledge graph on Neo4j. Reading its source and its eval code, three mechanisms buy the score, facts distilled from every message at ingest with relative dates resolved to absolute ones, entity summaries that pre-join what is known about a thing across sessions, and a cross-encoder reranking candidates before the reader sees them. Its winning configuration does no graph traversal at all.

The database is not the differentiator. Graphiti needs four generic capabilities from its store, vector search, keyword fulltext, string-keyed edges, bounded link-walks, and three of those already run in-process here, with no server to operate. Adopting a graph database would close none of the measured gaps.

The real difference is where the work happens: that pipeline spends an LLM call per message at ingest, so retrieval meets pre-digested facts. This one stores raw and searches raw, so retrieval is instant and lossless, and pays for it on questions that need distillation.
